# PP-OCRv6 替换方案设计

## 范围

本任务评估 PP-OCRv6 作为现有浏览器本地 OCR 流水线中的可选识别提供者。

首个实现目标是 `PP-OCRv6_small_rec`。如果 small 能成功转换为 ONNX、通过 ONNX Runtime Web 加载、正确解码，并通过浏览器冒烟测试，则第二个目标是 `PP-OCRv6_medium_rec`。现有文本检测器保持不变，PaddleOCR 仍然是可选路径，不会在本任务中成为默认 OCR 引擎。

## 已沉淀决策

- 先接 small，再看条件接 medium。
- small 成功的最低标准是：ONNX 转换成功、模型元数据匹配、浏览器中可以加载、CTC 解码可用、至少一次冒烟测试有结果。
- medium 不作为 small 的并行前置工作；只有 small 的链路跑通后才继续投入。
- 速度比较必须基于同一输入样本和同一测试脚本，避免把样本差异误认为模型差异。
- 本任务保留 v5 作为基线和回滚路径，不直接重命名或覆盖现有 `paddleocr_rec` 资产。

## 架构边界

- 保持当前默认内置 OCR 路径不变。
- 保留现有 PP-OCRv5 识别路径，作为回滚路径和基准测试基线。
- 为 v6 候选模型增加专用模型 id，而不是直接把当前 `paddleocr_rec` 改指到 v6。
- 如果 v6 ONNX 合约兼容，复用现有 Paddle 识别预处理和 CTC 解码代码。
- 注册 v6 专用字典，因为 PP-OCRv6 token 顺序与 PP-OCRv5 不同。
- 不引入 `@paddleocr/paddleocr-js`；本项目已经通过 `onnxruntime-web` 直接运行 ONNX。

## 模型资产

官方 PP-OCRv6 识别下载包是 Paddle 静态图归档，不是 ONNX 文件。实现时需要分别用 PaddleX/Paddle2ONNX 转换候选模型，并在浏览器接入前验证 ONNX 元数据。

根据官方元数据，预期识别模型合约如下：

- `PP-OCRv6_small_rec`：输入图像形状 `[3, 48, 320]`，CTC 字典条目 `18708`，输出类别 `18710`。
- `PP-OCRv6_medium_rec`：输入图像形状 `[3, 48, 320]`，CTC 字典条目 `18708`，输出类别 `18710`。

当前 v5 模型使用 `18383` 个字典条目和 `18385` 个输出类别，因此 v6 必须使用新生成的字典文件。只要 ONNX 输出仍为 `[N, T, C]` 或 `[T, C]`，blank id 为 `0`，并保留尾部 space 类别，现有 CTC decoder 应该仍然适用。

## 运行时流程

1. 用户选择 OCR 引擎。
2. 流水线使用现有 detector 检测文本区域。
3. 选中的 Paddle 识别提供者裁切每个检测区域。
4. 识别提供者通过 `modelRegistry` 加载对应模型 id。
5. 预处理把裁切图缩放到高度 `48`，宽度限制/填充到 `320`，归一化后生成 NCHW RGB 输入。
6. ONNX Runtime Web 通过项目常规执行后端回退链路执行推理。
7. CTC decoder 使用当前模型匹配的字典解码。
8. 后续字段补全、翻译、修补和排版逻辑保持不变。

## 识别提供者选择

当前识别提供者写死加载 `paddleocr_rec`。实现时应引入一个很窄的选择机制，例如识别提供者工厂，让同一套识别代码可以加载：

- 当前 v5 基线模型 id
- `PP-OCRv6_small_rec`
- small 成功后再加入的 `PP-OCRv6_medium_rec`

UI 可见标签需要保持中文。最稳妥的 UI 行为是保留已有设置兼容性，并且只在冒烟测试确认候选模型能在浏览器中加载后，再把新选项暴露给用户。

## 基准测试设计

基准测试需要在同一条件下比较已接入的 Paddle 识别变体：

- v5 基线
- v6 small
- v6 medium，仅在 small 成功且 medium 已接入后加入

基准测试输出应包含：

- 选择的 OCR 模型/识别提供者
- 浏览器中实际使用的执行后端，能获取时记录
- 冷启动模型/session 加载耗时
- 热识别耗时
- 总区域数量
- 有效 OCR 结果数量
- 单区域平均、p50、p95 耗时，条件允许时记录
- 代表性识别文本样例

至少使用一个日文漫画/条漫测试样本。如果没有更好的用户样本，使用 `benchmark/color/fixtures/` 中现有 OCR 测试样本。

## 兼容性说明

- PP-OCRv6 small/medium 都使用与 v5 不同的字典顺序，token id 不兼容。
- `webgpu`/`webnn` 可能拒绝 Node 或 WASM 可以运行的算子，因此必须做浏览器冒烟测试后再把候选模型视为可用。
- medium 明显大于当前 v5 mobile 和 v6 small，因此即使热推理质量提升，包体积、下载耗时和冷启动也可能是主要回退。
- 当前识别提供者串行处理每个区域。本任务应先测量这种现状，不在没有数据前引入 batching 或并发优化。
- 如果 v6 输出明显异常但元数据兼容，优先检查预处理细节，尤其是 RGB/BGR 通道顺序和归一化方式。

## 回滚策略

回滚应保持简单：

- 保留 v5 模型和字典注册。
- 保持现有内置 OCR 默认值不变。
- v6 选项使用专用模型 id 和设置项隔离。
- 如果转换、运行时或浏览器冒烟测试失败，移除或隐藏对应 v6 UI 选项。
