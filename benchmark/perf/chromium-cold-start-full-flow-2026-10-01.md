# Chromium 全流程冷启动耗时与减半预算

2026-10-01。生产代码 `f26f779`，包含 `29e31c8` 的历史着色器缓存。ORT Web 1.27.0 JSEP，Playwright Chromium 145.0.7632.6，RTX 5070 Ti / NVIDIA 610.74。沿用此前的 2921×4096 图片，保持全部模型和 float32 精度。

## 结论与计时口径

完整首图的最终三轮测量，从用户触发到结果图片解码并进入下一动画帧：

| 状态 | 三轮全程耗时 | 中位数 | 压缩到 50% 的目标 |
| --- | --- | ---: | ---: |
| 新进程、新 profile，无扩展着色器历史缓存 | 5691.0 / 5765.5 / 5222.8 ms | **5691.0 ms** | **2845.5 ms，约 2.85 秒** |
| 保留各自 profile 的缓存，关闭浏览器后重新启动，Session 重新创建 | 4901.6 / 4665.3 / 3770.4 ms | **4665.3 ms** | **2332.7 ms，约 2.33 秒** |

若继续用此前“约 5 秒”作基线，数学上的目标就是约 2.5 秒。新的数字同时明确了缓存状态、原文排版和最终显示的边界，适合后续验收。

本次使用生产扩展快捷图片处理路径和 `processMode=original`：包括取图、传输、宿主启动、字体、模型加载、检测、气泡检测、OCR、排序、遮罩、去字、排版、PNG 编码、结果传输、解码与下一动画帧，跳过外部翻译。排版使用识别出的原文，实际中文译文的排版成本仍可能不同。图片由本机 HTTP 服务提供，包含取图流程，但没有互联网下载波动；模型是现有本地扩展资源。

这里的冷启动指浏览器新进程、扩展宿主/Worker/Session 重新建立。未清除系统文件缓存和 GPU 驱动缓存。三轮样本不足以代表所有图片、GPU 和机器负载。

现有 `[shinobu:jank].totalMs` 在结果送回内容页时结束，早于图片显示。为本次分析补充了 `pipelineSummary`、`displayTailMs`、`visibleResultMs`。显示终点为 PNG 解码后下一次 `requestAnimationFrame`，不是物理显示器呈现时间；全图哈希校验放在该终点之后，避免校验自身拖慢计时。

## 全流程各阶段

下表使用无缓存全程中位数对应的 A 样本，避免把不同样本各阶段的中位数拼成不存在的一次运行。进度分段用于端到端分账，内部 `stageTimings` 用于解释子阶段，两者不会重复相加。

| 阶段 | 耗时 | 解释 |
| --- | ---: | --- |
| 配置、取图、输入传输、宿主就绪 | 882.3 ms | 首个 pipeline 进度之前的真实工作，尚未细分每一跳 |
| 宿主准备、字体等待、图片解码 | 308.1 ms | `runtime-prepare` 273.5 ms，`load` 34.6 ms |
| 检测模型加载 | 843.0 ms | 包含首次 Worker/ORT/WASM/设备/Session 路径，不能全部称为磁盘下载 |
| 文本检测 | 893.1 ms | GPU 预处理、首次模型执行、读回、CPU 后处理和预览画布 |
| 气泡检测 | 591.4 ms | Session 和首次执行成本混在本阶段 |
| OCR | 795.8 ms | 首次执行含编译/初始化，实际执行细节见下文 |
| 合并、误识别过滤、阅读顺序 | 133.6 ms | 其中顺序排序 124.8 ms |
| 遮罩细化 | 231.4 ms | 来自并行阶段的进度分段；内部计时约 232 ms |
| 去字 | 533.1 ms | 来自并行阶段的进度分段；内部计时约 533 ms |
| 排版原文 | 32.2 ms | 字体加载已在前面完成 |
| PNG 编码、Base64、传输和结果收集 | 317.9 ms | 内部 PNG 编码约 163.8 ms，其余约 154 ms |
| 图片解码和下一显示帧 | 126.3 ms | `visibleResultMs - totalMs` |
| 进度切换等剩余开销 | 2.8 ms | 完成切换、并行分支状态等 |
| **全程** | **5691.0 ms** | 分段和与总时一致，容许 0.1 ms 四舍五入 |

检测加载 + 检测 + 气泡 + OCR 共 **3123.3 ms，约 55%**；算上去字阶段，约 64%。这些阶段包含模型计算以外的初始化、编译、传输和后处理，不能把整个差值解释成 GPU 算力不足。

前面独立测量的同进程热态全程，到结果收集为止是 2175.6 / 3045.3 / 2092.7 ms，中位数 2175.6 ms。它证明目前有较大的冷启动开销，但不是“真正冷启动可以直接做到 2.18 秒”的证明。

前一个测量时段无缓存结果收集耗时为 5538.9 / 6778.6 / 6192.9 ms，中位数 6192.9 ms；最终时段同一生产代码为 5564.7 / 5479.7 / 5101.1 ms。未在两组之间实施性能优化，差异反映机器负载等波动。前述 6.19 秒不能和最终 5.69 秒当作提速结果比较。

## 翻译时间如何排除

生产流程的翻译和去字是并行分支：

`总时 = 前置阶段 + max(翻译时间, 遮罩细化 + 去字时间) + 排版 + 编码/交付/显示`

因此不能直接从总时减去完整的翻译时间。设外部翻译不再增加等待，剩余耗时应保留完整去字分支。本次 original 模式直接测这条路径。也不能同时相加 `parallel` 和其子阶段 `mask_refine` / `inpaint`。

## 优先优化点

### 1. 在用户触发时启动检测加载，与取图、字体重叠

当前取图完成并进入宿主后，`createImagePipeline.prepare()` 先注册两套字体并等待全部字体，之后才加载图片和 detector Session。字体并非检测所需输入，`drawTypeset()` 已有字体等待。

最小方向是让字体加载继续异步进行，到排版时再等待；按目标语言加载实际使用的字体。进一步在本地执行配置确定后启动宿主和 detector 准备，与原图下载/传输重叠，计时仍从同一次用户触发开始。

无缓存代表样本的“入口 + 字体/图片 + detector 加载”目前 **2.03 秒**，希望其串行关键路径预算降到 **0.90 秒左右**。这主要靠重叠已有工作，而不是让 95 MB 模型本身少算一半。具体可隐藏多少，需拆出各跳和 Worker/Session 的测量后确认。

不要把一次运行之前完成的预热计入真正冷启动的提速。

### 2. 把首图着色器编译从首次使用处提前

主线已经有历史 WGSL 缓存和四路 `createComputePipelineAsync()`，因此“增加历史缓存”不再是新方案。当前实现没有历史记录时不会提前编译。

真正无缓存首图的下一步，是先覆盖固定输入的 detector 1024、bubble 640、inpaint 512：提供与 ORT、模型、实际设备代码生成特征匹配的模板，取得 GPUDevice 后立即编译，与 Session 加载重叠。OCR 根据实际 width/batch 尽早准备必要的形状，控制未命中和重复编译，避免一次编译所有猜测组合。

若模板方案无法可靠覆盖设备差异，再评估 ORT 程序生成与异步编译链路的修改。仅把同步 `createComputePipeline()` 换成返回 Promise 不满足当前调用契约。

此前已有完整扩展实验：四路模板预编译与加载重叠，让首图中位数 4970.0 → 4223.2 ms；第二张图 3492.3 → 2512.75 ms。trace 显示同步管线创建累计 1246 → 12 ms，DXC 编译工作仍然存在，但移到后台并与其他工作重叠。见 `chromium-cold-start-experiments-2026-09-16.md`。这是方向证据，不能把 1246 ms 累计时间直接从当前全程扣掉，也不能把已上线的缓存收益再算一次。

[WebGPU 管线异步创建文档](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/createComputePipelineAsync)说明它在管线可使用后完成，以避免编译阻塞 GPU 执行。模板命中、实际并发和 Chromium/Dawn 复用仍需本项目的端到端实验验证。

### 3. 删除未使用的全图工作，减少像素来回转换

正常扩展结果没有使用检测/OCR 的预览 Canvas，但 orchestrator 仍无条件执行两次 `drawRegions()`，复制整张 2921×4096 画布。先按需生成这些预览，可以保持正式结果相同，并减少两张约 48 MB RGBA 画布的拷贝/驻留。

遮罩路径多次经过 `binary mask → Canvas/RGBA → getImageData → binary mask`，包括放大到原图尺寸后再次逐像素阈值化。应复用已经算出的 mask/灰度数据，减少重复读回和扩展到整图的次数，保留现有插值、阈值和输出尺寸。阅读顺序本身已使用缩小图和可分离高斯，不应再建议“改成可分离高斯”作为新优化。

输入当前是后台下载后 Base64 回到内容页、转 Blob，再通过 Port 转 Base64 送到宿主。可以让图片字节在扩展侧直接交给宿主，减少这一来回。结果也有 `Canvas.toDataURL → Blob → Base64 → Blob` 的转换链，可研究复用已有编码字节。

[Chrome 官方消息文档](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#serialization)规定 runtime 消息使用 JSON 序列化，所以这需要调整数据交付路径，不能直接在现有 Port 上套用 Worker 的 transferable。现有同步 PNG 导出是为了避开 offscreen 文档异步 `toBlob` 的 idle 等待；简单换回 `toBlob` 不是已验证的提速。

这部分对有历史缓存的冷启动尤其重要；此时模型首次编译已被削弱，CPU、图片往返和最终显示占比上升。

### 4. OCR 仅回传解码需要的结果

独立详细诊断样本 `08-06-55-717Z.json` 的 OCR 797.2 ms 可分为：预处理 76.6 ms、模型调用 665.2 ms、CTC 解码 10.7 ms、颜色采样 38.6 ms，余量约 6 ms。同 Worker 热态模型调用 76.4 ms。冷态前两次调用约 487.2 / 102.8 ms，之后每次约 8–17 ms，说明首次初始化/编译很重要。

本图输出概率矩阵总计 **35,099,960 bytes，约 35.1 MB**。当前 Worker 对 GPU 输出也会调用 `getData()` 后返回完整矩阵。仅开启 `preferredOutputLocation: 'gpu-buffer'` 不能省掉这一步。

可在同一 GPUDevice 上对概率做 float32 ArgMax/最大概率提取，只回传 token 和对应概率，然后继续当前 CTC blank、去重、置信度逻辑。按本图时间步数，索引 + 最大概率约 3.8 KB；模型、输入、精度均不需改变，但必须验证并列值、NaN 处理和结果一致性。

这是补充收益候选，热态全部模型调用只有约 76 ms，CTC CPU 解码约 9 ms，不能仅因输出有 35 MB 就预支数百毫秒或数秒的收益。首次编译和加载仍优先。[ORT 官方 IO binding 文档](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html#keep-tensor-data-on-gpu-io-binding)描述了保持输出在 GPU 上以减少传输的接口。

## 达到 50% 的预算

下表是希望达到的串行关键路径预算，不是优化后实测或可保证的预测。重叠的资源工作只计一次。

| 无缓存首图分组 | 当前代表样本 | 目标预算 | 需要减少 |
| --- | ---: | ---: | ---: |
| 取图、字体、宿主/运行时、图片解码、detector 加载 | 2.03 秒 | 0.90 秒 | 约 1.13 秒 |
| 检测、气泡、OCR | 2.28 秒 | 0.90 秒 | 约 1.38 秒 |
| 遮罩、去字、排序、排版和少量状态切换 | 0.93 秒 | 0.65 秒 | 约 0.28 秒 |
| 编码、交付、解码、显示帧 | 0.44 秒 | 0.40 秒 | 约 0.04 秒 |
| **合计** | **5.69 秒** | **2.85 秒** | **约 2.84 秒** |

因此，减半需要“提早加载 + 取图/字体重叠”和“首次编译重叠”两项产生主要收益，再由减少画布/像素工作补齐。只换 detector 的执行实现、只优化排版或只开一个 session 参数，不足以覆盖 2.84 秒。

若以保留缓存后首图 4.67 秒作为目标，则需要约 2.33 秒。可设准备/加载 0.75 秒、检测/气泡/OCR 0.60 秒、遮罩/去字/排序/排版 0.58 秒、交付/显示 0.40 秒的预算。该场景的重复着色器缓存收益已计入基线，更依赖前置重叠和 CPU/数据路径改进。

原生 WebGPU EP 的已有实验不能计入本预算：独立 detector 有收益，但同 Worker 的全局 Session 队列明显拖慢端到端；分离 detector Worker 能运行，却未改善全程。Graph capture 主要省重复 dispatch，首次 capture 仍需初始化与编译，而且有静态形状/全 WebGPU 节点等条件，不能先算成冷启动的主要收益。[ORT 性能文档](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html#try-using-graph-capture)列出了适用条件。

## 下一步最小实验

1. 先做字体等待后移，以及从同一用户触发开始的 detector 提前加载；只测这一个改动的相邻冷/热对照。
2. 再做固定形状首图模板的 A/B，确保全新 profile 也有收益，并检查已有缓存和热态不退化。
3. 目标仍有缺口时，先删未使用的预览画布、复用 mask 数据和减少图片往返，再测 GPU CTC。

每一步同时保留 `totalMs`、`visibleResultMs`、Session/模型阶段与输出一致性。不同阶段的累计收益不能直接相加，最终只按同一输入、同一缓存状态的全程验收。所有本次正式样本的结果 RGBA SHA-256 均为 `d3bd5084867c64501ac615d6baacb8cb31ee38f6b93af28cb7ce78f2d1d8ba97`。

本次未修改生产流水线、模型或精度；修改了现有 benchmark 的采集范围并保存分析。Chromium 扩展构建、benchmark TypeScript 检查和阶段和/结果哈希校验通过。
