# 系统修复竖排标点与拉丁字符方向

## Goal

建立一套可验证、可扩展的竖排字形方向系统，修复当前 `~ / ～ / 〜`、日文长音符 `ー`、破折号以及拉丁字符在竖排漫画文本中的错误形态和方向，同时保留已经稳定的气泡定位、源文本几何、字号拟合、分栏与禁则处理。

用户最终应看到符合日中竖排习惯的标点和假名变体；英文单词、缩写及短数字应按明确且一致的规则排版，而不是全部逐字符直立堆叠。

## Background and confirmed facts

- 当前 `CJK_H2V` 把 `~`、`〜`、`～` 全部替换为 `︴`，不同语义和字形被压成同一个短波形，因此会出现用户看到的怪异形态。
- 当前映射没有覆盖日文长音符 `ー`（U+30FC）；它在竖排中仍以横线直接绘制。用户观察到的“破折号”在现有 14 张 fixture 中主要是这个字符，而不是 U+2014 `—`。
- 当前竖排布局把文本拆成单个字符，`VerticalGlyph` 只有 `ch` 和 `advanceY`；Canvas 渲染对每个字符直接执行 `strokeText` / `fillText`，无法表达旋转字形、连续英文 run 或纵中横。
- 当前 `bench:render` 和评分主要检查列数、矩形、字号、水平偏移和字符中心位置，不检查字形栅格、旋转方向或英文 run 连续性，因此几何高分不能证明竖排字形正确。
- 既有任务已把字号、字形步进、内容高度和气泡扩展高度解耦；本任务必须在该契约上增加方向能力，不能用重新耦合这些量的方式修复视觉问题。

## Requirements

### 1. 统一的竖排方向规则

- 以 Unicode Vertical Orientation（UAX #50）为基础，对 grapheme cluster 分类，而不是仅按 UTF-16 code unit 或单个 code point 处理。
- 运行时使用固定版本、离线可用的紧凑规则表；不在浏览器运行时访问网络。
- 区分“保持直立”“顺时针旋转 90°”“优先使用竖排变体、无变体时直立”“优先使用竖排变体、无变体时旋转”四类语义。
- 现有 `CJK_H2V` 只保留为经过验证的竖排替换表，不再同时承担字符方向判断。

### 2. 标点与假名变体

- `~`、`〜`、`～` 不得无条件折叠成同一个 `︴`；应按各自 Unicode 方向和字体能力选择竖排替代或旋转回退。
- `ー` 必须在竖排中呈现为纵向长音符，并在 Source Han Sans 字体栈下有确定的 Canvas 回退方案。
- U+2014 `—`、U+2015 `―`、连接号、下划线、省略号、括号和句读点需纳入同一方向管线，避免继续增加互相冲突的特殊分支。
- 竖排替换或旋转后，字形中心、墨迹框和纵向步进应保持稳定，不得引入明显偏移或重叠。

### 3. 拉丁字符与数字

- 连续拉丁文本先形成 run，再按策略决定整体旋转、逐字直立或纵中横；不能在分类前丢失单词边界。
- 英文单词和品牌名应尽量作为原子 run 换行；只有整个 run 无法放入单列时，才按明确的回退规则切分。
- 短缩写、单个拉丁字符及短数字应有可配置、可测试的判定规则。
- 默认采用 mixed 策略：英文单词/品牌整体顺时针旋转 90°；1–4 个全大写字母及单个字母保持直立；1–2 位数字使用纵中横；更长数字作为旋转 run。

### 4. 句末双标点组合

- 翻译文本或显式分段末尾恰好连续两个 ASCII 问号/感叹号时，将 `!?`、`?!`、`!!`、`??` 中的任一组合识别为一个 `tate-chu-yoko` item，在一个 CJK em 方框内按原顺序从左到右横向直立显示。
- 全角形式及 ASCII/全角混合形式采用同一布局策略，例如 `！？`、`？！`、`！！`、`？？`、`!？`；debug 与回溯数据必须保留原始字符和顺序。
- 当双标点后面仅有句末闭合引号或闭合括号时，仍视为句末组合；闭合符号自身继续按原竖排规则布局。
- 双标点必须在单字符 `! -> ︕`、`? -> ︖` 替换之前识别，并作为原子 item 参与换列和禁则处理。
- 单个问号/感叹号、非句末双标点以及三个或更多连续问号/感叹号不套用本规则，继续按基础竖排方向处理，避免擅自压缩强调程度不同的标点串。

### 5. 布局与渲染契约

- 用可区分的布局 item 表达直立字形、旋转 run 和纵中横；布局结果必须携带原文、显示文本、方向、纵向步进和可观测边界。
- 方向分类发生在分栏和换行之前；分栏仍遵守现有禁则、preferred columns、源行几何和气泡 mask。
- 旋转 run 使用其真实横排测量结果计算墨迹框和纵向占用，不得继续用 `国` 的横排 Canvas box 代替所有情况。
- 描边与填充必须复用同一个变换路径，避免边框和正文旋转角度或中心不一致。
- 源文本几何仍是列锚点和步进的重要输入；方向重构不得让气泡扩展高度反向影响字号或源字符步进。

### 6. 可观测性与基准评分

- 调试输出增加 grapheme/run 的原文、方向类型、旋转角度、显示文本、边界框和纵向步进，同时保持现有字段可读或提供明确版本迁移。
- 为波浪线、长音符、破折号、括号、省略号、单个拉丁字符、英文单词、全大写缩写、短数字和句末双标点建立专门的确定性 fixture。
- 评分报告新增独立的字形方向与 run 连续性指标；旧几何 composite 分数不得继续被解释为完整的竖排视觉质量。
- 浏览器截图回归使用固定 Chromium、固定 bundled font 和固定 DPR；纯逻辑测试覆盖分类与布局，减少仅靠像素 golden 导致的脆弱性。
- 当前 14 张 fixture 必须继续通过严格审计，并作为真实案例回归集，特别覆盖第 7、12、13、14 张中已观察到的问题。

### 7. 兼容性与性能

- 不改变 OCR、翻译、修复图像或横排排版的产品行为；共享 helper 的修改必须有横排回归测试。
- 保持纯前端、离线运行，不引入完整 HarfBuzz/FreeType WASM 作为本次修复的前置条件。
- 对常见短气泡文本，新增 grapheme 分类和 run 合并不得造成可感知的渲染延迟。
- 使用严格 TypeScript 类型和判别联合；不以 `any` 或散落的布尔组合表达方向状态。

## Acceptance Criteria

- [x] `~●`、连续 `～～` / `〜〜` 不再统一渲染成短而怪异的 `︴`；专用浏览器 fixture 与方向断言通过。
- [x] `そうだねーー` 中两个 U+30FC 均呈纵向长音形态，步进一致且不与相邻假名重叠。
- [x] U+2014 `—`、U+2015 `―` 与日文 `ー` 被识别为不同输入，并分别走可解释、可测试的方向/替换路径。
- [x] `AveMujica` 按确认后的默认策略形成连续 run，不再无条件逐字直立并在列间任意断开。
- [x] 单个 `N`、全大写短缩写、1–2 位数字和更长数字分别符合已确认的 mixed 策略，且都有布局单元测试。
- [x] `真的吗!?`、`真的吗?!`、`真的吗!!`、`真的吗??` 均形成单个纵中横 item，在一个 em 内保持各自原始顺序横向显示。
- [x] 全角、半角及混合宽度组合和闭合符号场景（如 `真的吗！？`、`真的吗?！」`）采用相同策略，原始字符可从 debug 数据回溯。
- [x] 单个问号/感叹号、非句末双标点以及 `!!!`、`???`、`!?!` 等三字符以上标点串不被误判为本规则的纵中横 item。
- [x] 直立字形、旋转 run 和纵中横的描边/填充中心一致；调试 overlay 能显示其方向、边界和旋转信息。
- [x] 现有 CJK 标点映射、禁则、源文本几何、分栏、气泡 mask、旋转四边形和横排路径的相关测试无回归。
- [x] 新报告同时给出旧几何分数和独立的 glyph-orientation / run-continuity 结果，并能让旧实现对新增 fixture 明确失败。
- [x] 14 张当前 fixture 重新 `bench:render` 后全部生成 render、overlay、debug 产物，严格审计通过，问题案例经人工复核无上述异常。
- [x] `npx tsc --noEmit --pretty false`、`npm run test`、`npm run build` 以及任务中列出的 benchmark 检查全部通过。

## Out of Scope

- 为 Canvas 引入完整的通用文字塑形引擎，或把整个排版器改写为 DOM/SVG。
- 修改 OCR 识别结果、翻译文本内容或自动把误识别字符替换成另一语义字符。
- 重新设计所有横排策略；仅允许为共享数据结构和 helper 做兼容性调整。
- 在本任务中解决所有复杂双向文本、任意数学公式或完整 ruby 注音排版。

## Resolved Product Decisions

- 采用推荐 mixed 策略：英文单词/品牌整体旋转，全大写短缩写及单个字母直立，1–2 位数字纵中横，更长数字整体旋转。
- 句末恰好两个问号/感叹号的所有组合（`!?`、`?!`、`!!`、`??`）及其全/半角等价形式模仿两位数字，使用纵中横；单个、非句末及三个以上标点串不自动压缩。
- 当前没有阻塞规划的开放产品问题；进入实现前只需用户审阅并批准本任务文档。
- U+30FC `ー` 的 `Tr` 回退不受连续或句尾上下文影响；不得增加“句尾连续 `ーー` 保持横向”的特判。
- OCR 输出保持层间隔离；`_lll` 等误识别不在 typeset 层纠正，也不得据此增加重复 Latin 直立规则。
- 旋转细线 glyph 与其他 item 共用统一描边样式，不做 source-specific `lineWidth` 调整。
